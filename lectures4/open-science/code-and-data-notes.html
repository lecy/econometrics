Research Integrity and Evidence Synthesis

Code and Data for the Social Sciences

An executive summary of Gentzkow and Shapiro’s practitioner’s guide (2014) for Unit 25. Most empirical research is writing and debugging code, and most researchers never learned to do it well. The guide takes seven practices from software engineering and database design and translates them for social scientists. This page summarizes each practice, shows what it looks like in R, and connects it to the replication problems from earlier units. Read the guide (PDF, 44 pages).

Section one

Key concepts

The argument of the guide in five claims.

Key concepts

Most reproducibility failures are engineering failures.

Files that moved, merges that silently dropped rows, sample definitions copied into dozens of scripts, a research assistant’s directory no one can rerun. None of these is fraud or bad statistics. Each is a problem that software engineers and database designers solved decades ago.

If an industry exists to solve your problem, learn what it does.

The authors’ rule of thumb: when billion-dollar firms and whole university courses are devoted to a problem you face, find out what the experts do before inventing your own fix.

The code is the record of what was done.

A result produced by pointing and clicking has no authoritative definition. A result produced by a script that runs from raw data to final table does. The script can’t be incomplete or out of date in the way a readme can.

Every second copy of a fact is a future contradiction.

copied code → inconsistent samples  ·  stale comments → code and notes disagree  ·  repeated attributes → conflicting values

Abstraction, normalized data, and self-documenting code are three versions of one idea: store each piece of information once.

Small fixed costs beat large repeated ones.

You will run every step more times than you expect. Automating, versioning, and testing cost a few days up front and pay for themselves within a project.

Section two

The problem: a self-taught approach that stops scaling

Chapter 1. Five situations the authors kept running into.

Gentzkow and Shapiro note that few economists, political scientists, or psychologists have formal training in computing. Most picked up programming along the way and never thought about it again. That worked until their projects grew. They describe five situations that will be familiar to anyone who has worked on a long project:

  1. Replicating an early draft fails because the code calls files that have since moved. Once the files are found, the estimates come out different.
  2. A regression has suspiciously few observations. A merge on county had dropped every row with a missing county code, and restoring them changes the results a lot.
  3. A referee asks for a different sample definition. The definition had been pasted into dozens of scripts, and some copies had drifted, so different tables used different samples.
  4. A research assistant leaves hundreds of files with long comments. Working out which to run, and in what order, takes days. In the end the code is rewritten from scratch.
  5. Three people share data files on a network drive, and every change one makes breaks the others’ code.

Their early response was to write more protocols, more comments, and more documentation for their assistants. It didn’t work. The turning point came when a computer scientist showed them how to organize a large dataset, and they realized they had been re-solving, badly, problems with well-known solutions.

Section three

The rules at a glance

Seven chapters, sixteen rules. Each prevents a specific kind of failure.

ChapterRulesThe failure it prevents
2. Automation (A) Automate everything that can be automated. (B) Write a single script that executes all code from beginning to end. Results with no record of how they were made; hours lost redoing manual steps.
3. Version control (A) Store code and data under version control. (B) Run the whole directory before checking it back in. Files named cleandata_022613_jms.do; not knowing which script made which output; a coauthor’s change breaking your code.
4. Directories (A) Separate directories by function. (B) Separate files into inputs and outputs. (C) Make directories portable. Rerunning the whole data build to change one regression; not knowing which files a script needs; code that only runs on one computer.
5. Keys (A) Store cleaned data in tables with unique, non-missing keys. (B) Keep data normalized as far into your code pipeline as you can. Datasets whose rows and columns can’t be interpreted; silent merge errors; the same attribute taking different values.
6. Abstraction (A) Abstract to eliminate redundancy. (B) Abstract to improve clarity. (C) Otherwise, don’t abstract. Copy-and-paste errors that run without complaint and give wrong answers.
7. Documentation (A) Don’t write documentation you will not maintain. (B) Code should be self-documenting. Comments that contradict the code, leaving no way to tell which is right.
8. Management (A) Manage tasks with a task management system. (B) E-mail is not a task management system. Two people each thinking the other is doing a robustness check; no record of what was decided.

Section four

Chapter by chapter

The guide works through one running example: did the arrival of television raise potato chip sales? Its code is in Stata. The R versions here are ours.

Automation

Most researchers learn early to put their analysis in scripts. The guide pushes further: every step, from converting the raw file to compiling the paper, should run from one master script. That script is both the build instructions and the documentation of the build order. Unlike a readme, it can’t be incomplete or out of date. The test is simple: delete every output file, run the master script, and get everything back. The authors learned this the hard way. They exported 200 files from a spreadsheet by hand, and then the provider sent an update.

# run_all.R: rebuilds every output from raw data
unlink(c("output", "temp"), recursive = TRUE)   # nothing survives from earlier runs
dir.create("output"); dir.create("temp")
source("code/01_import.R")
source("code/02_clean.R")
source("code/03_merge.R")
source("code/04_models.R")
source("code/05_tables.R")
quarto::quarto_render("paper.qmd")

Version control

Dating and initialing files (regressions_022713_mg.do) is meant to preserve history. In practice it creates confusion about which script produced which log and which data. Version control keeps one authoritative version, records every change and its author, and lets you undo anything. The second rule matters as much as the first: before committing, run the whole project from the top. If every committed version has been run end to end, checking it out later returns exactly the same results. The guide (2014) used Subversion and mentions Git as worth a look. Today Git with GitHub is the default.

Directories

Split the project by function, for example a build directory that turns raw data into a clean file and an analysis directory that turns the clean file into tables and figures. Give each the same subfolders: input, code, output, temp. Now you can change a regression without rebuilding the data, and anyone can see which files the analysis depends on. Use relative paths so the project runs on any machine. The authors also point the analysis at a fixed revision of the data, so an upstream change can’t break downstream code without warning.

project/
  build/      input/  code/  output/  temp/
  analysis/   input/  code/  output/  temp/

# paths relative to the project root, not C:/Users/...
library(here)
counties <- read.csv(here("build", "output", "counties.csv"))

Keys

The chapter’s example is a population file that mixes county and state variables. The state population is filled in for some counties and missing for others, and two counties in one state sit in different regions. No one can say what the file means. The database answer is to store each kind of entity in its own table. Each table has a key, a variable (or set of variables) that is unique and never missing, and each variable lives in the table whose entity it describes. County population goes in the county table, state population in the state table, and the county table carries state as a foreign key. Data stored this way are normalized. The recommended pipeline has three steps:

  1. Store the raw data in normalized tables that preserve everything in the source.
  2. Add derived variables, and variables from other sources, still in normalized tables.
  3. Merge into the one rectangular file the model needs, and do no data manipulation at this step.
stopifnot(!anyNA(county$county_id), !anyDuplicated(county$county_id))
stopifnot(!anyNA(state$state),      !anyDuplicated(state$state))

analysis <- dplyr::left_join(county, state, by = "state",
                             relationship = "many-to-one")   # errors if state is not a key
stopifnot(nrow(analysis) == nrow(county))                      # no rows gained or lost

Abstraction

The guide’s example computes a leave-out mean three times by copying and editing code. Two of the three copies carry editing errors, the code still runs, and the results are silently wrong. A single function called three times removes both the redundancy and the chance of error, and its name says what it does. The third rule is a brake: don’t write general tools for things you will do once. For functions you will reuse, write unit tests, small scripts that check the function on known inputs, so it can be changed safely later.

leaveout_mean <- function(x, group) {
  total <- ave(x, group, FUN = function(v) sum(v, na.rm = TRUE))
  count <- ave(!is.na(x), group, FUN = sum)
  (total - x) / (count - 1)
}

# unit test: the leave-out mean of (1, 2, 3) is (2.5, 2, 1.5)
stopifnot(all.equal(leaveout_mean(c(1, 2, 3), c(1, 1, 1)), c(2.5, 2, 1.5)))

Documentation

This chapter argues for less documentation. A comment explaining that an elasticity equals 0.4 / 0.2 = 2 sits above code that now passes 3. Whichever was updated last, nobody can tell which is right. Any second representation of a fact will eventually disagree with the first, and comments are the worst case, because nothing breaks when they go stale. So write only documentation you will keep as current as the code, and put the information in the code itself: compute the elasticity from named quantities, so the number and its derivation can’t drift apart. Comments still earn their place for things code can’t hold, such as the source of a number or why a formula that looks wrong is right. And if an input must never be allowed, write code that rejects it rather than a comment that warns against it.

# Source: Shapiro (2005), Table 2A
pct_change_quantity <- -0.4
pct_change_price    <-  0.2
elasticity <- pct_change_quantity / pct_change_price

Management

An e-mail thread among three coauthors ends with nobody sure who is running which robustness check, or whether the salsa control was meant to enter in logs or levels. A task tracker fixes this. Each task has an owner, a description, a status, and its own discussion, and that record is still there months later. The guide names Asana, Wrike, Flow, and JIRA, plus a shared notebook for less structured notes. For a project already on GitHub, GitHub Issues does the same job.

Section five

The appendix on code style

Code has two audiences: the computer, and the next person who has to read it.

  • Keep it short and purposeful. Lines under about 100 characters, functions under about 80 lines, scripts no more than a few hundred. Every script and function should have one clear purpose.
  • Make functions “shy.” Declare inputs and outputs, pass only what is needed, and avoid global variables.
  • Order code for reading top to bottom. Put helper functions right after the functions that call them.
  • Use descriptive names. Good names replace comments. Avoid pairs like x and xx. Short names are fine for algebra kept close to where they are defined.
  • Set off the key calculations. Break long formulas into named steps, and keep the full derivation in a separate document when it is complicated.
  • Write logical tests the way you would say them. “All entries are zero” is clearer than “the maximum is zero.”
  • Be consistent. The team’s convention matters more than which convention it is.
  • Check for errors where it pays. That means guarding against infinite loops and destructive inputs, and replacing cryptic error messages with clear ones. Turn “x must be a vector” comments into code that stops.
  • Write tests. Economists test code by hand. Writing the test down takes no longer and never has to be repeated.
  • Profile slow code, store “too much” output from it, and keep it apart from fast code. Rerunning an hour-long estimation to reorder a table is waste.

Section six

Connections to the course

The failures in earlier units were often failures of these practices.

  • Two copies of one fact. In the Nye et al. replication, a report’s appendix repeated one table row under the wrong heading. Shin and Chung’s meta-analysis gives different counts of published studies in its abstract and its methods. Each is the documentation problem in Chapter 7: the same information stored twice, with nothing forcing the copies to agree.
  • Results with no build record. Shin and Chung publish no list of their 120 effect sizes. Their Grade 5 row could be reverse-engineered only because one study supplied all of it. A coded-data file and the script that pools it would have made every row checkable.
  • Keys and dependence. Seven of Shin and Chung’s 17 “studies” report the same STAR first graders. A coding sheet with a dataset and cohort key, as in the replication case studies, is the database fix: one table of samples, and effect sizes that point to it.
  • Automation in the replications. Each class size case study is one R script. It enters every number with its table and page, rebuilds every effect size from those numbers, and writes the coded CSV. Rerunning it reproduces the guide’s tables, and changing one decision changes every number that depends on it.
  • The omission bias replication. The authors posted their data and code, which made the replication possible. It also made it possible to find what their published code got wrong.

What has changed since 2014. The guide’s practices have held up; the tools have moved on. In R, an RStudio project or the here package handles relative paths, Git and GitHub handle version control and issues, testthat handles unit tests, and targets or a Makefile handles the build. renv records package versions, which the guide does not cover. Peikert, van Lissa, and Brandmaier (2021), the other reading this unit, combine these tools into one workflow. These tool names are this page’s additions, not the guide’s.

Section seven

A checklist for your own project

If you can answer yes to each, a stranger can rerun your analysis.

  1. Can you delete every output file and get it all back by running one script?
  2. Is the project under version control, and did you run it end to end before your last commit?
  3. Are raw data read-only, and are inputs, code, outputs, and temporary files in separate folders?
  4. Does every path work on someone else’s computer?
  5. Does every cleaned table have a key that is unique and never missing, and does every merge check that no rows were gained or lost?
  6. Is any piece of code, sample definition, or parameter written in more than one place?
  7. Is there a comment that would be wrong if someone changed the code beneath it?
  8. Is there one place that records who is doing what, other than your inbox?
