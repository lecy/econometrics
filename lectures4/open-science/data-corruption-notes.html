Data Corruption: When Files Change Without Telling You

An introduction to A Taxonomy of Data Corruption for Unit 25. Data can be damaged without anyone making a typo or doing anything wrong. All it takes is opening a file in the wrong program and clicking Save. This page explains how that happens, walks through examples of each kind of damage, and ends with five habits that prevent most of it. Read the full taxonomy (PDF, 21 pages).

Section one

Key concepts

The whole idea in five claims.

Key concepts

A data file is just a string of characters.

A CSV file doesn’t say whether 00501 is a number or a label, or whether 03/04/2026 means March 4 or April 3. The rules for reading it, called a schema, are not stored in the file.

So software guesses.

Every program that opens a file has to decide what each value is. Excel, R, and Python all make these guesses for you, and they usually guess right. That’s why it’s easy to stop paying attention.

Corruption is a wrong guess that nobody reports.

The ZIP code 00501 becomes the number 501. The gene name SEPT2 becomes the date September 2. The file still opens normally, and no warning appears.

The test is a round trip.

write the file → read it back → compare  ·  anything different = corrupted

The damage is rarely random.

Wrong guesses hit some kinds of values more than others: ZIP codes in the Northeast, names with accents, dates early in the month. That means corruption can bias a result, not just add noise.

Section two

Files have no instructions

Why a computer has to guess, and why that’s a problem.

Suppose a friend texts you “meet me 03/04.” If your friend is American, that probably means March 4. If your friend is British, it means April 3. You can ask. A computer opening a file can’t.

A CSV file is the most common way to share data, and it is about as simple as a format can be: values separated by commas, one row per line. Here is a tiny one:

zip,name,visit_date
00501,José,03/04/2026

To use this file, a program has to answer questions the file never answers:

  • Is 00501 a number (in which case the zeros mean nothing) or a code (in which case they matter)?
  • How was the letter é in José stored as bytes?
  • Is 03/04/2026 a date, and if so, which date?

Each program answers these questions with its own built-in guesses. When a guess is wrong, the value changes, and nothing tells you it happened. The taxonomy calls this data corruption. It needs no broken hardware and no bad luck. It is the normal behavior of normal software.

What this page does not cover. Typos, wrong formulas, and deliberate tampering also damage data, but they have different causes. This page is only about damage caused by software guessing wrong.

Section three

The round-trip test

Write the data, read it back, and compare.

Opening a CSV in Excel and clicking Save, without touching a single cell, is a complete round trip. Excel guesses once when it opens the file and again when it saves it. Here is a four-column file before and after:

As written

zip,account,gene,lot
00501,1234567890123456789,SEPT2,1E5
02134,1234567890123456790,MARCH1,2E3

After open and save in Excel

zip,account,gene,lot
501,1.23457E+18,2-Sep,1.00E+05
2134,1.23457E+18,1-Mar,2.00E+03

Every column changed:

  • zip: the leading zeros are gone. You can add them back, but only if you know every ZIP code has five digits.
  • account: Excel keeps only 15 digits, so the last digits were replaced. Two different accounts are now the same number, and nothing in the file can tell you which was which.
  • gene: the gene names turned into dates.
  • lot: the product codes were read as numbers in scientific notation (1E5 = 100,000).

Section four

Six layers where a guess can go wrong

Going from bytes on a disk to a number you can analyze takes six steps. Each step is a place where corruption can get in.

LayerThe question being guessedA wrong guess looks like
1. EncodingWhich characters do these bytes stand for?José becomes JosÃ©
2. StructureWhere does each cell and row begin and end?Values land in the wrong column, or rows vanish
3. TypeIs this text, a number, a date, TRUE/FALSE, or missing?00501 becomes 501
4. ConventionWhich format was this written in?03/04/2026 read as April 3
5. MeaningWhat does this value refer to?3, with no record that it means “High”
6. WriterDid the saving program write what it held?3.14159 saved as 3.14

Two things to keep in mind. First, errors cascade: if a value lands in the wrong column (layer 2), you’ll then see text in a number column (layer 3). So when something looks wrong, check the lowest layer first. Second, layer 5 is different. Layers 1 to 4 are wrong guesses, but no program can guess what 3 means or what units a number is in. That information is simply lost unless a data dictionary travels with the file.

Layer 1

Encoding: bytes to characters

Computers store letters as numbers, and there is more than one table for translating between them. The letters A to Z are the same in almost every table, but accented letters are not. If a file is saved with one table (usually UTF-8) and opened with another, accented letters come out garbled:

As written (UTF-8)

id,name,city
1,José,Tempe
2,Zoë,Mesa
3,Müller,Yuma

Read with the wrong table

ï»¿id,name,city
1,JosÃ©,Tempe
2,ZoÃ«,Mesa
3,MÃ¼ller,Yuma

The strange ï»¿ in front of id is a hidden marker some programs put at the start of a file. Now the first column is no longer called id, so code that asks for id fails.

A quieter problem is invisible characters. "Tempe" and "Tempe " (with a space at the end) look identical on screen, but a computer sees two different cities. When you merge two files on city name, the rows with the extra space silently fail to match.

Prevention: save files as UTF-8, tell R the encoding when you read a file, and trim extra spaces from text when you import it.

Layer 2

Structure: characters to cells

A CSV uses commas to separate cells. So what happens when a value itself contains a comma?

id,name,city
1,Smith, John,Tempe

The reader sees four cells instead of three. John moves into the city column, and Tempe falls off the end. Quotation marks are meant to protect values like this ("Smith, John"), but a single stray quote can do even more damage:

As written: 6 people

id,name,city
1,Smith,Tempe
2,Jones,Mesa
3,"Lee,Phoenix
4,Diaz,Yuma
5,Kim",Tucson
6,Ortiz,Flagstaff

What the reader finds: 4 people

id  name                            city
1   Smith                           Tempe
2   Jones                           Mesa
3   Lee,Phoenix4,Diaz,Yuma5,Kim     Tucson
6   Ortiz                           Flagstaff

Diaz and Kim no longer exist, Lee now lives in Tucson, and Python’s pandas library gives no warning.

Spreadsheets cause structural problems too. A sheet made for people to read often has a title row, a blank spacer row, and a “Total” row at the bottom. Read as data, the total becomes an extra observation and every sum doubles. And Excel has a hard limit of 1,048,576 rows. Anything past that is never loaded, and saving the file writes the shortened version over the original.

Prevention: one header row, one observation per row, nothing else on the data sheet. Check the number of rows before and after every step.

Layer 3

Type: cells to text, numbers, and dates

This is the most common layer. Programs try to be helpful by turning anything that looks like a number or date into one. The victims are almost always codes and identifiers: values made of digits or short letter strings that were never meant to be counted.

ValueWhat it really isWhat it becomes
00501ZIP code501
1234567890123456789Account number1.23457E+18 (last digits lost forever)
SEPT2, 5-12Gene name; apartment numberSeptember 2; May 12
FFemaleFALSE (in R, if every row is F)
NANamibia’s country codeMissing
+14805551234Phone number14805551234, or a formula error

R and Python decide the type of a whole column at once, which creates a different trap. Imagine a column of 10,000 test scores where one person typed unknown. R can’t store a word in a number column, so it makes the entire column text. Now mean(score) fails, and in older versions of R a quick fix with as.numeric() could return category codes instead of the actual scores.

Prevention: tell R the type of each column when you read the file, and always read identifiers (ZIP codes, IDs, phone numbers) as text.

Layer 4

Convention: which format was it written in?

Here the program gets the type right but reads the format wrong. The result looks perfectly reasonable, which makes this layer hard to spot. Dates are the classic case. A collaborator in the UK records visit dates as day/month/year:

As written (day/month)

id,visit_date
1,03/04/2026
2,13/04/2026
3,04/03/2026
4,31/12/2025

Opened and saved on a US computer

id,visit_date
1,3/4/2026
2,13/04/2026
3,4/3/2026
4,31/12/2025

Rows 1 and 3 are now real dates, but swapped: April 3 became March 4. Rows 2 and 4 couldn’t be read as US dates (there is no 13th month), so they stayed as text. The column is now half wrong dates and half text, and the only visible clue is a missing zero.

Another example is missing-value codes. Many surveys record “no answer” as -99. Software sees a valid number:

income (thousands): 40, 52, 61, -99, 47

mean with -99 included:  20.2
mean of the real values: 50.0

Other conventions that trip up readers: two-digit years (45 is 1945 in Excel but 2045 in R), decimal commas (1,234 means 1.234 in Germany), and decorated numbers like $1,200 or 45%.

Prevention: write dates as YYYY-MM-DD (2026-04-03), always use four-digit years, store plain numbers without symbols, and leave missing cells empty.

Layer 5

Meaning: what does the value refer to?

At this layer every character survives, but the information needed to understand it is lost. This usually happens when data moves from a richer format (an R data frame, a Stata or SPSS file) into a CSV, which has nowhere to store it.

id,satisfaction,region
1,Medium,3
2,High,1
3,Low,3

Nothing here is wrong, but a lot is missing:

  • Nothing says that Low < Medium < High, so R sorts them alphabetically: High, Low, Medium.
  • Nothing says that region 3 means “West.”
  • A fourth level, “Very high,” that nobody chose has disappeared completely.
  • A survey that distinguished “refused to answer” from “question not asked” now has just a blank for both.

Units are lost the same way. Is 450 in dollars, thousands of dollars, or 2015 dollars? And since ZIP codes and county codes are made of digits, software will happily calculate an “average ZIP code” or treat a county code as a measurement in a regression.

Prevention: this layer can’t be fixed inside the CSV. It needs a second file, a data dictionary, that lists every variable’s name, type, units, category labels, and missing-value codes. Putting units in the column name (revenue_usd_thousands) also helps.

Layer 6

Writer: did the file get what the program held?

Layers 1 to 5 go wrong when a file is read. Layer 6 goes wrong when it is saved, so the file looks perfectly clean. You only notice by comparing it to the original. When Excel saves a CSV, it writes what each cell displays, not what it stores:

Stored in the workbook

org_id:  123456789012
revenue: 1250000.4999
margin:  0.123456
date:    2026-03-15

Written to the CSV

org_id:  1.23457E+11
revenue: 1250000.5
margin:  12.35%
date:    Mar-26

The ID lost six digits, the margin lost precision and gained a percent sign, and the date lost its day. On the next read it may even come back as March 26 of the current year. Formatting choices someone made to make the sheet look nice have become permanent data loss.

Spreadsheet users also store information in ways a CSV can’t hold. “Rows highlighted in yellow should be excluded” is lost the moment the file is saved as CSV. And R’s write.csv() adds row numbers as an extra first column unless you tell it not to.

Prevention: save data from code rather than from Excel’s Save As, use row.names = FALSE in R, and record exclusions in an actual column (exclude = 1), not as a color.

Section five

How serious is it?

Four questions to ask about any case of corruption.

QuestionRangeExample
Would anyone notice?Loud (error), quiet (a warning that scrolls by), silentA semicolon file read as one column is loud. A day-month swap is silent.
Can it be undone?Reversible, fixable with outside knowledge, permanentGarbled accents can be fixed if caught early. A truncated account number is gone.
How much is affected?One cell, a column, rows, the whole fileA stray quote can swallow many rows.
Who is affected?Every value, or only some kindsLeading-zero loss only hits ZIP codes that start with 0.

The last question matters most. This kind of corruption is almost never random:

  • ZIP codes starting with 0 are in New England, New Jersey, and Puerto Rico. If they fail to match in a merge, your “national” sample quietly loses a region.
  • Encoding errors only hit names with accents, so people with Spanish, Vietnamese, or German names are the ones dropped when records are matched by name.
  • Day-month swaps only happen for dates on the 1st through 12th of a month.
  • Treating NA as missing removes Namibia, and only Namibia.

When errors are tied to geography, ethnicity, or time, they don’t just add noise. They can bias your results, which makes this a question of research validity and not only data cleaning.

The six to learn first. These are silent, permanent, and selective all at once: long identifiers losing digits, text turned into dates, day-month swaps, stray quotes swallowing rows, rows cut off at size limits, and Excel saving what it displays instead of what it stores.

Section six

Real cases

This isn’t hypothetical. Each case traces back to default software behavior with no warning.

CaseWhat happened
Gene names in published research, 2005–2020 A 2016 scan of genetics journals found gene names converted by Excel (like SEPT2 to a date) in about one in five papers that included gene lists. A 2021 follow-up found errors in 30.9% of such articles from 2014 to 2020 (3,436 of 11,117). The problem got worse, not better.
Genes renamed to fit Excel, 2020 The committee that names human genes gave 27 genes new names so they would survive spreadsheets: MARCH1 became MARCHF1 and SEPT1 became SEPTIN1. Scientists changed their data to fit the tool.
England’s COVID-19 case counts, 2020 Public Health England loaded lab results into the old Excel .xls format, which stops at 65,536 rows. Each case took several rows, so a sheet held only about 1,400 cases. The overflow was dropped, and 15,841 positive cases from September 25 to October 2 were left out of daily counts and contact tracing.

One caution: the researchers who documented the gene-name errors have said no case is known in which these errors changed a study’s conclusions. The evidence shows how common the errors are, not how much harm they caused.

Section seven

Try it yourself: a canary file

Coal miners carried canaries because the birds reacted to danger first. A canary file is built to break first.

Every column below holds values chosen to break under one kind of corruption. Copy it into a plain text editor (Notepad, TextEdit in plain-text mode, or RStudio) and save it as canary.csv.

row,zip,long_id,gene,sex,country,phone,visit_date,price,name
1,00501,1234567890123456789,SEPT2,F,NA,+14805551234,03/04/2026,"$1,200",José
2,02134,1234567890123456790,MARCH1,F,NO,+14805551235,13/04/2026,$950,Zoë
3,85004,1234567890123456791,DEC1,F,US,+14805551236,04/03/2026,"$12,050",Müller
4,10001,1234567890123456792,OCT4,F,NA,+14805551237,31/12/2025,$80,Nguyễn
  1. Open the file in a tool (Excel, Google Sheets, R, or Python) with the default settings, and save it under a new name without editing anything.
  2. Open both files in a text editor and compare them line by line.
  3. For each value that changed, write down which layer it belongs to, whether the tool warned you, and whether you could rebuild the original from the new file alone.
  4. Try again, this time telling the tool to treat every column as text. Did the problems go away?

Expect most columns to change in Excel. R’s read.csv() leaves the gene names and dates alone, but it drops the zeros from the ZIP codes, loses digits from the long IDs, drops the + from the phone numbers, turns the column of Fs into FALSE, and treats Namibia as missing. No tool is safe by default, and the tools don’t agree with each other. What a file contains depends on which programs it passed through, which is a good reason to write that path down.

Section eight

Five habits that prevent most of it

Every defense either removes the need to guess or catches a wrong guess afterward.

  1. Raw data are read-only. Keep the file exactly as you received it in a data-raw folder, and never open it by double-clicking. If you need to look at it in Excel, use Data > From Text/CSV and set the columns to text.
  2. Every CSV travels with a data dictionary. The dictionary is the missing schema: a table of column names, types, formats, units, category labels, and missing-value codes.
  3. Read files with a script that states each column’s type. If you let the software guess, you’ve made a decision without writing it down. 
    library(readr)
d <- read_csv("data-raw/survey.csv",
              col_types = cols(zip = col_character(),
                               id  = col_character()),
              na = "")
  4. Check every hand-off. Record the number of rows when data comes in and after every step that could change it, such as a merge. When data moves between programs or people, run a round trip and compare. 
    nrow(d)                    # before
d2 <- merge(d, counties, by = "fips")
nrow(d2)                   # after: did any rows disappear?
  5. Identifiers are text. If doing arithmetic on a column would be meaningless, it isn’t a number, whatever it looks like.

These habits fit the project structure in Code and Data for the Social Sciences: raw data kept separate and never edited, every step done in code, and documentation that travels with the data.
